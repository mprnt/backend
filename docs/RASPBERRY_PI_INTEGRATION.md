# MPrnt — Raspberry Pi Integration Contract

**Audience:** the engineer building the Raspberry Pi print client.
**Status:** this document is the single source of truth for the Pi ↔ backend contract.
If the code and this document disagree, the document is wrong — raise it.

The backend owns the queue, the money and the document storage. The Pi owns CUPS
and the physical printer. The only coupling between them is the HTTP contract below.

---

## 1. Endpoint and transport

| | |
|---|---|
| **Base URL (production)** | `https://<your-railway-domain>/api/v1` |
| **Base URL (local dev)** | `http://<laptop-lan-ip>:3000/api/v1` |
| **Transport** | HTTPS only in production. TLS is terminated at the platform edge. |
| **Content type** | `application/json; charset=utf-8` on every request with a body |
| **Time** | All timestamps are ISO-8601 with an explicit `Z` (UTC) |

Rules for the Pi:

- **Verify the TLS certificate.** Do not pass `verify=False` to `requests`, not even
  temporarily. A kiosk on untrusted campus Wi-Fi is exactly the threat model here.
- **Never accept a plain-HTTP production URL.** If the configured base URL does not
  start with `https://` and the host is not a private address, refuse to start.
- Set a request timeout on every call (10s connect, 30s read is a reasonable default).
- Send a `User-Agent` such as `mprnt-pi/1.0 (RPI_M001_01)` so the backend logs are readable.

## 2. Authentication

Two different credentials, used at two different moments.

### 2.1 Enrollment (once per device, by a human)

```
POST /queue/printers/enroll
X-Provisioning-Token: <deployment secret, from the backend operator>
```

```json
{
  "printerId": "RPI_M001_01",
  "kioskId": "11111111-1111-4111-8111-111111111111",
  "name": "Kiosk M001 - Printer A",
  "ipAddress": "192.168.1.50",
  "capabilities": {
    "supportsColor": false,
    "supportsDoubleSided": true,
    "maxCopies": 50,
    "supportedPaperSizes": ["a4"]
  }
}
```

**201 response — the only time the API key is ever shown:**

```json
{
  "status": "success",
  "data": {
    "printerId": "RPI_M001_01",
    "apiKey": "mprnt_pk_2Nf8xQ...43-chars...",
    "keyPrefix": "mprnt_pk_2Nf8xQ",
    "issuedAt": "2026-09-28T09:00:00.000Z",
    "kioskId": "11111111-1111-4111-8111-111111111111"
  }
}
```

The backend stores only a SHA-256 digest of this key. It cannot be recovered — if it
is lost, an admin rotates it and the Pi is reconfigured.

- Re-enrolling an existing printer returns **409**. Use rotation instead.
- Rate limited to 5 attempts per 15 minutes per IP.
- `kioskId` is the **UUID** from the `kiosks` table, not the short code `M001`.
  Ask the backend for it; do not guess.

**On the Pi:** write the key to `/etc/mprnt/printer.env`, owner `root:mprnt`, mode
`0640`. Never commit it, never log it, never print it in an error message.

### 2.2 Every other call (on each request, by the client)

```
X-Printer-Id:  RPI_M001_01
X-Printer-Key: mprnt_pk_2Nf8xQ...
```

- **401** — missing or wrong credentials. Do not retry in a tight loop; back off
  and alert. A 401 means misconfiguration, not a transient fault.
- **403** — the key was revoked, or the job is not assigned to this printer.
- **429** — polling too fast. Honour `Retry-After` and back off.

The printer's identity is taken **from these headers only**. `printerId` in a request
body is ignored, so a bug on one Pi cannot affect another.

## 3. Job identity

| | |
|---|---|
| **Format** | UUID v4, lowercase, canonical 8-4-4-4-12 hyphenated form |
| **Example** | `9f1c2e4a-7b3d-4c6e-9a10-5d8e2f4b1c03` |
| **Source** | `print_jobs.id` — generated by the backend at job creation |

This one value identifies the job everywhere: in `/queue/poll`, in the status URL,
in WebSocket events and on the customer's receipt.

- The Pi **never generates** a job ID. Echo back exactly what you were given.
- Treat it as an opaque string. Do not parse it, re-case it or strip hyphens.
- Safe as a temp filename: `/var/spool/mprnt/<jobId>.pdf`. Validate it matches
  `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`
  before using it in a path, so a malformed response can never cause a path escape.

## 4. Claiming a job

```
POST /queue/poll
X-Printer-Id / X-Printer-Key
```

Body is optional; send your current capabilities for logging:

```json
{
  "capabilities": {
    "supportsColor": false,
    "supportsDoubleSided": true,
    "maxCopies": 50,
    "supportedPaperSizes": ["a4"]
  }
}
```

> The server matches jobs against the capabilities **stored at enrollment**, not
> the ones you send. To change them, call `POST /queue/printers/register`.

**Nothing to print (the common case):**

```json
{ "status": "success", "message": "No jobs available", "data": null }
```

**A job, claimed exclusively by you:**

```json
{
  "status": "success",
  "message": "Job assigned",
  "data": {
    "jobId": "9f1c2e4a-7b3d-4c6e-9a10-5d8e2f4b1c03",
    "documentUrl": "https://s3.ap-south-1.amazonaws.com/mprnt-documents/...&X-Amz-Signature=...",
    "documentUrlExpiresAt": "2026-09-28T09:15:00.000Z",
    "fileName": "assignment.pdf",
    "fileSizeBytes": 204800,
    "mimeType": "application/pdf",
    "settings": {
      "colorMode": "bw",
      "copies": 2,
      "pageRange": "all",
      "customRange": null,
      "printSides": "double",
      "paperSize": "a4",
      "orientation": "portrait"
    },
    "totalPages": 10,
    "assignedAt": "2026-09-28T09:00:00.000Z",
    "leaseExpiresAt": "2026-09-28T09:15:00.000Z",
    "attempt": 1
  }
}
```

### Field notes

- **`documentUrl`** — pre-signed S3 URL, valid for 15 minutes. Download it
  immediately and never cache or log it: the URL *is* the authorisation.
- **`leaseExpiresAt`** — finish and report before this, or the backend assumes the
  Pi died and gives the job to another printer. If a job will legitimately take
  longer, keep sending `printing` updates — each one extends the lease.
- **`attempt`** — `1` on first try, higher after a retry. If `attempt > 1`, a previous
  printer may have produced partial output; useful for operator logging.
- **`settings.pageRange`** is `"all"` or `"custom"`. When `"custom"`, honour
  `customRange` (e.g. `"1-3,7,9-11"`). **Validate it before passing it to CUPS** —
  accept only digits, commas and hyphens; reject anything else rather than
  forwarding it to a shell.
- **`copies`** multiplies pages: a 10-page job with `copies: 2` prints 20 sheets.

### Polling rules

- Poll every **5 seconds** while idle.
- On an empty queue, back off gently (5s → 10s → 30s) to reduce load; reset on a job.
- **One job at a time.** Do not poll again until the current job reaches a terminal state.
- If the Pi restarts mid-print, the next poll returns **the same job** with a fresh
  `documentUrl`. Treat that as resume, not as a new job.

## 5. Downloading the document

```
GET <documentUrl>
```

Plain HTTPS GET. **Send no auth headers** — the signature is in the URL, and adding
an `Authorization` header will make S3 reject the request.

Before printing, verify:

1. HTTP status is `200`.
2. `Content-Length` matches `fileSizeBytes` (allow the header to be absent).
3. The file begins with `%PDF-`.

If any check fails, report `failed` with `errorCode: "DOWNLOAD_FAILED"` — do not
send an unverified file to the printer.

There is **no other way** to fetch the document. The Pi has no access to
`/documents/:id/download`; that route serves the customer's own session, not printers.

## 6. Reporting status

```
POST /queue/jobs/{jobId}/status
X-Printer-Id / X-Printer-Key
```

```json
{
  "status": "printing",
  "printedPages": 6,
  "errorCode": null,
  "errorMessage": null,
  "timestamp": "2026-09-28T09:03:12.000Z"
}
```

| Field | Required | Notes |
|---|---|---|
| `status` | ✅ | `printing` \| `completed` \| `failed` \| `cancelled`. `queued` and `assigned` are server-owned and rejected. |
| `printedPages` | on `printing` / `completed` | Cumulative sheets, counting copies. Clamped server-side to `totalPages × copies` and never allowed to move backwards. |
| `errorCode` | **required when `failed`** | From the table below. |
| `errorMessage` | optional | Free text, ≤1000 chars, shown to the operator. Never put a URL or key in here. |
| `timestamp` | optional | When the Pi observed it. The server timestamps authoritatively; this is for correlation. |

**Response:**

```json
{
  "status": "success",
  "data": { "jobId": "9f1c...", "status": "printing", "applied": true }
}
```

> **Counting sheets, not pages.** `printedPages` counts physical sheets, so a
> 10-page job with `copies: 2` completes at `printedPages: 20`. The customer-facing
> status endpoint returns both `totalPages` (10) and `totalSheets` (20); compare
> progress against `totalSheets`.

`applied: false` means the job was already in a terminal state and the update was
ignored — that is a success, not an error. Stop retrying.

### Error codes

| Code | Meaning | Backend behaviour |
|---|---|---|
| `OUT_OF_PAPER` | Tray empty | Requeue if retries remain |
| `PAPER_JAM` | Jam detected | Requeue if retries remain |
| `OUT_OF_TONER` | Toner/ink exhausted | Requeue if retries remain |
| `PRINTER_OFFLINE` | CUPS cannot reach the printer | Requeue if retries remain |
| `DOWNLOAD_FAILED` | Could not fetch or validate the PDF | Requeue if retries remain |
| `UNSUPPORTED_DOCUMENT` | Not a printable PDF | Requeue (will exhaust and fail) |
| `CUPS_ERROR` | CUPS rejected the job | Requeue if retries remain |
| `TIMEOUT` | Print did not finish in time | Requeue if retries remain |
| `UNKNOWN` | Anything else | Requeue if retries remain |

After **3 attempts** the job is marked permanently failed and becomes eligible for
refund. The Pi does **not** implement its own per-job retry loop — report the
failure and let the backend decide.

### Required lifecycle

```
poll → (job)
  ├─ POST status  printing    (once, as the job starts)
  ├─ POST status  printing    (periodically, with printedPages — extends the lease)
  └─ POST status  completed   (printedPages = totalPages × copies)
                  or failed   (with errorCode)
```

**The terminal update is not optional.** A job that never gets one sits in
`printing` until its lease expires, which delays the customer's refund or reprint.

### Retrying a status post

A dropped status update loses money. The Pi must:

1. Retry with exponential backoff (1s, 2s, 4s, 8s…, capped at 60s).
2. **Persist unsent terminal updates to disk** and resend them after a restart.
3. Keep retrying a `completed` indefinitely — it is idempotent and safe.

Do not swallow the failure with a log line and move on.

## 7. Heartbeat

```
POST /queue/heartbeat
```

```json
{
  "status": "online",
  "currentJobId": "9f1c2e4a-7b3d-4c6e-9a10-5d8e2f4b1c03",
  "paperLevel": 72,
  "inkLevel": { "black": 40, "color": null },
  "errorMessage": null
}
```

`status` is one of `online`, `busy`, `error`, `maintenance`, `offline`.
Omit `printerId` — it comes from the headers.

**Response:**

```json
{
  "status": "success",
  "data": { "serverTime": "2026-09-28T09:00:00.000Z", "pendingJobs": 1 }
}
```

- Send **every 30 seconds**, from a thread independent of printing — a Pi busy
  printing must still heartbeat.
- No heartbeat for **180 seconds** marks the printer offline and stops it being
  given new work. It recovers automatically on the next heartbeat.
- `serverTime` lets the Pi detect clock drift; log a warning past ~60s of skew.

## 8. Reference client loop

```python
def main_loop():
    start_heartbeat_thread()          # every 30s, independent of printing
    flush_persisted_status_updates()  # resend anything unsent from a previous run

    backoff = 5
    while True:
        job = poll()                  # POST /queue/poll
        if job is None:
            sleep(backoff)
            backoff = min(backoff * 2, 30)
            continue

        backoff = 5
        try:
            report(job, "printing", printed_pages=0)
            path = download_and_verify(job)          # size + %PDF- magic
            print_via_cups(job, path, on_page=lambda n: report(job, "printing", n))
            report(job, "completed", job["totalPages"] * job["settings"]["copies"])
        except DownloadError as e:
            report(job, "failed", error_code="DOWNLOAD_FAILED", error_message=str(e))
        except CupsError as e:
            report(job, "failed", error_code="CUPS_ERROR", error_message=str(e))
        finally:
            shred(path)               # remove the customer's document
```

## 9. Security requirements on the Pi

The Pi holds other people's documents and a credential to the print queue. Treat it
as a production secret handler.

1. **Delete every document after printing**, on the success path and every failure
   path. Spool to `/var/spool/mprnt` (mode `0700`, owned by the service user), not `/tmp`.
2. **Never log** `documentUrl`, `X-Printer-Key`, or document contents. Log `jobId`,
   status and error code only.
3. **Run unprivileged.** A dedicated `mprnt` system user, not `root`, not `pi`.
   Grant only CUPS access.
4. **No inbound ports.** The Pi makes outbound calls only. Nothing should listen
   on the network; the backend never connects to the Pi.
5. **Validate `customRange`** against `^[0-9,\-]+$` before it reaches CUPS, and use
   `subprocess` with an argument list — never `shell=True` with interpolated values.
6. **Full-disk encryption** on the SD card if the kiosk is physically accessible;
   a stolen card otherwise yields the API key.
7. **Auto-restart** via systemd (`Restart=always`, `RestartSec=10`) with the key
   supplied through `EnvironmentFile=/etc/mprnt/printer.env`.
8. **Rotate the key** if the device is replaced, repaired or de-commissioned. Ask
   the backend operator to call the rotate endpoint; the old key dies immediately.

## 10. Quick reference

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/queue/printers/enroll` | `X-Provisioning-Token` | One-time enrollment → API key |
| POST | `/queue/printers/register` | Printer key | Refresh capabilities/IP on boot |
| POST | `/queue/heartbeat` | Printer key | Health, every 30s |
| POST | `/queue/poll` | Printer key | Claim next job, every 5s |
| POST | `/queue/jobs/{jobId}/status` | Printer key | Report progress/outcome |
| GET | `/queue/jobs/{jobId}` | none | Job status (kiosk frontend); returns `printedPages`, `totalPages`, `totalSheets`, `copies` |
| GET | `/queue/status` | Admin JWT | Queue statistics |
| GET | `/queue/printers` | Admin JWT | Fleet listing |
| POST | `/queue/printers/{printerId}/rotate-key` | Admin JWT | Issue a new key |
| POST | `/queue/printers/{printerId}/revoke` | Admin JWT | Disable a printer |

### Error envelope

Every error uses the same shape:

```json
{ "status": "error", "message": "This job is not assigned to your printer" }
```

| Status | Meaning | Pi action |
|---|---|---|
| 400 | Validation error | Bug — fix the payload, do not retry |
| 401 | Bad/missing credentials | Stop, alert; do not hot-loop |
| 403 | Revoked, or job not yours | Drop the job, re-poll |
| 404 | Unknown job or printer | Drop the job, re-poll |
| 429 | Rate limited | Back off, honour `Retry-After` |
| 5xx | Server problem | Exponential backoff, keep retrying |

## 11. Local development

The backend operator provides `PRINTER_PROVISIONING_TOKEN` and a `kioskId`.
Against a laptop on the same LAN, `http://<laptop-ip>:3000/api/v1` is acceptable
**for development only** — production must be HTTPS.

```bash
# 1. Enroll (once) — save the returned apiKey
curl -sX POST http://localhost:3000/api/v1/queue/printers/enroll \
  -H 'Content-Type: application/json' \
  -H "X-Provisioning-Token: $PRINTER_PROVISIONING_TOKEN" \
  -d '{"printerId":"RPI_DEV_01","kioskId":"<kiosk-uuid>","name":"Dev Printer",
       "capabilities":{"supportsColor":false,"supportsDoubleSided":true,
                       "maxCopies":50,"supportedPaperSizes":["a4"]}}'
```

```bash
# 2. Poll for work
curl -sX POST http://localhost:3000/api/v1/queue/poll \
  -H 'Content-Type: application/json' \
  -H 'X-Printer-Id: RPI_DEV_01' -H "X-Printer-Key: $PRINTER_API_KEY" -d '{}'
```

```bash
# 3. Report completion
curl -sX POST http://localhost:3000/api/v1/queue/jobs/<jobId>/status \
  -H 'Content-Type: application/json' \
  -H 'X-Printer-Id: RPI_DEV_01' -H "X-Printer-Key: $PRINTER_API_KEY" \
  -d '{"status":"completed","printedPages":10}'
```

A job only becomes pollable after its payment is captured — `/queue/poll` will
return `null` for an unpaid job by design.
